# 10 分钟演示路线

适用：信息化、业务系统管理、软件开发相关岗位。使用模拟设备与人员；开始前按各仓库 README 准备环境。终端测试也可以作为现场演示备选。

## 0–2 分钟：说清问题

以设备点检为主线：设备台账、任务、异常和缺陷之间需要可追溯关系；流程不能只靠前端按钮限制，后端必须校验。说明作品是个人原型及自己的实际参与范围，包括 AI 辅助开发部分。

## 2–6 分钟：演示已验证的流程规则

设备点检项目提供数据库回归测试，可在 backend 目录运行：

```sh
python -m pytest tests/test_operation_integrity.py -v
```

| 情景 | 预期行为 | 讲解重点 |
|---|---|---|
| 两个模拟步骤按顺序 PASS | 完成后读取数据库仍有执行人、结果、签名记录 | 页面成功之外还要验证持久化 |
| 直接执行第二步 | 返回 409，保持原记录 | 前后端双重约束 |
| 第一步 FAIL | 保存失败，阻止后续步骤与覆盖 | 异常流程也是业务需求 |
| 最后一步 FAIL | 不标记完成 | 真值判断不能代替业务语义 |
| VIEWER 执行步骤 | 返回 403 | 后端角色边界 |
| 草稿附带伪造 PASS/执行人 | 清除执行字段 | 输入可信度与字段白名单 |

失败后由主管核实、作废并重新开票是本原型规则，不是现场操作指导。尚未验证并发双击/多终端竞争，不能宣称具备完整的并发幂等保证。

## 6–8 分钟：展示工程维护

展示一次 PR 的代码差异、测试结果和前端构建。解释为何锁定前端依赖、为何保留失败用例，以及 CI 的实际状态。若 GitHub Actions 尚未运行，展示本地日志并明确两者区别。

## 8–10 分钟：映射岗位能力与下一步

| 面试问题 | 可据实讲述的内容 |
|---|---|
| 你如何理解需求？ | 把“不能跳步、失败不能完成”转成状态和接口约束 |
| 为什么需要测试？ | 发现并修复数据库 JSON 嵌套更新与状态判定问题 |
| 如何跟业务人员合作？ | 用正常/异常场景请对方确认，形成验收用例 |
| 如何考虑上线？ | 当前缺少生产验收，下一步补并发控制、迁移、备份恢复和权限审计 |
| 做出了什么收益？ | 报告可复核的代码和测试成果；没有测量依据时不报节省金额或工时 |

## 简历表述素材

按自己实际完成和理解程度组织措辞：围绕电厂设备点检场景维护 FastAPI、React 业务原型；修复操作票顺序与结果校验，补充数据库回归测试；为多个业务模块增加自动构建与测试检查。

不要把原型写成公司投产项目，也不要把 AI 生成但自己无法解释的部分写成独立掌握。
