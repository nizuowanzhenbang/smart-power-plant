## 实际差异与影响

| 对象 | 当前字段事实 | 下一批应解决的问题 |
|---|---|---|
| 供应商 | 采购有唯一code及name；煤质只有本库id和唯一name | 同名/改名不能自动证明同一供应商；本库id不可跨库直接等同，需显式来源及映射 |
| 订单与煤批次 | 采购contract_no/order_no，各有本库外键；煤质batch_number及supplier_id，无采购订单外键 | 订单可分多批、同批可涉及不同运输；先定义关联粒度，不能令order_no等于batch_number |
| 设备与机组 | 设备code与equipment_system/location；机组code和本库unit_id，设备模型未见机组外键 | 需明确设备归属机组及多机共用设备规则，不能凭EQ前缀或位置文字决定归属 |
| 热值 | 煤质Qnet,ar为kcal/kg、Qgr,ad为kcal/kg；能效coal_lhv/design_coal_lhv为kJ/kg | 指标名称、单位、收到/干燥基等一起传递；低/高位热值不可只改单位就当同指标 |
| 硫/灰基准 | 煤质全硫/灰分在实际模型标d，能效设计灰分ar；采购规格灰/硫只标% | 未声明的基准须明确“未知/待确认”，不得静默认作ar或d；不重写PP-020既有口径 |
| 金额 | 采购unit_price为元/吨、total_amount/planned_amount为万元；设备estimated_amount为元 | 传输金额必须声明CNY和倍率，杜绝同名amount值混加 |
| 时间 | 采购/煤质/设备多用UTC naive默认；能效DateTime(timezone=True)并以UTC aware默认 | 发布接口统一显式时区，先核对业务输入与旧数据来源，不能给所有历史naive时间猜时区 |

既有煤质换算使用4.1868 kJ/kcal：4000 kcal/kg按相同约定为16747.2 kJ/kg。下一批应复用已发布常数及标记，不另选4.184造成跨系统差异。该算术已用Decimal核对，不是测量数据或已交付适配器。

## 建议下一批四个独立验收单元

1. 身份：来源系统+实体类型+来源稳定ID构成外部引用；建立明确映射与冲突状态，保留本库主键。先覆盖两系统id=1碰撞、供应商改名、重复/不一致映射；无证据不自动按名合并。
2. 指标：版本化指标名、单位、基准、精度和原始值；选择煤质Qnet,ar→能效入炉低位热值的单条适配示例，明确批次到工况的时间/归属联系；缺基准及不匹配拒绝或标未知。
3. 时间：显式UTC输出与原始时区来源，业务发生时间/接收时间分别保留；覆盖+08:00等价、无时区历史来源未知、跨日边界，不覆盖原整改锚点。
4. 血缘与反馈：每条适配结果带来源记录、固定契约版本和换算声明；先用合成场景实际串起一次数据传递，再安排PP-060约束寻优，不把设计的统一字典当联合优化已实现。

第一项具体动作：resume/claim PP-050后复核上述固定源码与当前HEAD，再给身份映射和一个实际热值适配通路设计最小范围；按RED→GREEN实施。PP-031/042/043三项审查小项可以另外集中处理，原采购/联动已交付保护不重做。未读取的运输/煤场/排放等字段留待该链路需要时核对，不每轮全库扫描。
