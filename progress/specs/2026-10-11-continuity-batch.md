# 接续补强设计 · PP-003/004/005

用户已批准审查方案并要求自主、批量交付。本轮主代理顺序实现，发布后接续煤质 PP-020。中央开工 f8e9c06，使用外置隔离工作树，保留已有业务及他人 PR。

使用 Python 标准库命令 `python -m progress_tools`，不引入服务或模型定时开发。`progress/SESSION.json` 保存一个活动认领和最后交接；四份核心 Markdown 保持可读，CURRENT 引用 SESSION 作为实时认领来源。RELEASES.json 只索引纳入本轮核验的固定交付，覆盖范围明确。

- resume：先取得中央 main SHA，以同一 SHA 读取四份核心文件、SESSION；输出可独立恢复的内容和 SHA。访问失败非零退出，不假装已读取。
- claim/checkpoint/release：单个活动认领，任务/执行者/仓库/分支/UTC/阶段/下一动作明确。写入以读到的中央 HEAD 为父创建 Git 提交，非强制更新 main ref；分支在读后前进则冲突拒绝，不能覆盖其他会话。完成/已有覆盖任务不得认领，其他执行者不可修改或释放；接管必须提供旧执行者和理由并保留历史。checkpoint 验证代码 SHA 在远端存在，merged 阶段要求实际 PR 合并 SHA 一致。保存代码本身仍通过其业务分支提交推送，检查点不替代代码发布。
- check --offline：核心文件、Markdown 本地链接、编号重复/状态、SESSION 结构、固定版本格式与交付索引一致性；畸形 JSON/未知任务拒绝。
- check --remote：固定代码提交、PR 合并 SHA 与指定检查均成功；缺失/未完成/失败、403/限流、超时均报告失败。CI 对 push/PR 自动执行离线及在线核验，使用只读 token。
- 阶段保存：决策/复现/实现/审查/PR/合并分别记录 phase、代码 SHA、真实验证摘要、下一动作；新环境 fresh-context 审查只从远端恢复，记录实际报告。

SESSION 是跨会话协作约定，Git ref 更新保护中央状态，业务代码与文档不构成跨仓库事务，也不能证明模型读懂或现场有效。user 新指令优先。默认每次对话完成多个可独立验收单元，批次内一个认领活动；不为了数量重做已有成果。
